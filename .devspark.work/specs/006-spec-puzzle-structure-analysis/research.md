# Phase 0 Research: Puzzle Structure, Challenge, and Character

No `NEEDS CLARIFICATION` markers remain in Technical Context — every technical unknown was resolved directly against the existing codebase (`scripts/puzzle/*.gd`, `tests/*.gd`, `tests/run_puzzle_regressions.py`) rather than requiring external research, since this feature adds no new dependency, platform, or technology to an already-established GDScript/Godot 4.4 project. The tasks below consolidate the concrete implementation-pattern decisions this plan depends on, each grounded in a specific existing file read during planning.

## Decision: `PuzzleAnalyzer` reuses `PuzzleSolver.analyze()` and a disposable internal `PuzzleState`, never a second rules engine

- **Decision**: `PuzzleAnalyzer.analyze(definition)` calls `PuzzleSolver.analyze(definition)` once internally to obtain `valid`, `solvable`, and `witness`, and constructs its own short-lived `PuzzleState` instances (one for the initial-state metrics, and one advanced step-by-step through the witness for the legal-choice-sequence/cascade metrics) purely as read-only rule-evaluation helpers. All blocking checks route through `PuzzleState.is_blocked`/`get_arrow_head`; the dependency graph's edges are derived by scanning `PuzzleDefinition.forward_ray_cells` and `get_cell_owners()` exactly as `PuzzleState._is_head_blocked` already does, not by re-encoding the blocking rule independently.
- **Rationale**: `scripts/puzzle/puzzle_solver.gd`'s own header comment states the monotonicity proof this plan must not contradict or re-derive incorrectly; reusing it directly guarantees agreement. `scripts/puzzle/puzzle_state.gd`'s `is_blocked`/`select_arrow`/`get_snapshot` are already public and side-effect-contained per instance, so a fresh internal instance is trivially disposable with no shared mutable state risk (matching exactly what `PuzzleSolver.analyze()` already does with its own fresh `PuzzleState`).
- **Alternatives considered**: Re-deriving blocking purely from `PuzzleDefinition` geometry without any `PuzzleState` — rejected, this would be a second, independently-maintained implementation of the exact blocking rule `PuzzleState.is_blocked` already owns, risking silent drift and directly violating spec FR-004's "MUST NOT introduce a second, independently-implemented rules engine."

## Decision: Dependency graph and cascade data are plain `Dictionary`/`Array` structures, not a new public class

- **Decision**: The dependency graph is represented internally and in the returned analysis dictionary as adjacency data (e.g. `{head: Vector2i -> blocked_by: Array[Vector2i]}` and its inverse), plus scalar/derived metrics (depth, longest chain, max in-degree, component count). Per-step cascade data is an `Array` of integers (newly-legal-arrow counts) aligned index-for-index with the witness `Array[Vector2i]` `PuzzleSolver.analyze()` already returns.
- **Rationale**: `PuzzleSolver.analyze()` already establishes the project's precedent for a domain analysis result being a plain `Dictionary` of primitives/arrays rather than a bespoke class (`.knowledge/architecture/arrow-puzzle.md`'s "Solvability Analysis" section documents this contract). Matching that shape keeps `PuzzleAnalyzer.analyze()` consumable the same way, including by a future generation spec, with no new serialization or validation surface for a dedicated graph class.
- **Alternatives considered**: A dedicated `PuzzleDependencyGraph` RefCounted class with its own methods — rejected as unnecessary ceremony for this scope; revisit only if a future generation spec needs graph mutation/traversal operations beyond read-only metrics.

## Decision: Analyzer tests join the existing bare-isolated-project regression harness rather than a new temp-project setup

- **Decision**: `tests/puzzle_analyzer_check.gd` is added to the same bare isolated temp project `tests/run_puzzle_regressions.py`'s `run_rule_regressions()` already builds for `puzzle_regression.gd` and `puzzle_catalog_check.gd`, copying `puzzle_analyzer.gd` alongside the other `scripts/puzzle/*.gd` files already copied there. It reports its own `PUZZLE_ANALYZER_FAILURES=0` marker, additive to the existing `PUZZLE_FAILURES=0`/`PUZZLE_CATALOG_FAILURES=0` markers.
- **Rationale**: `tests/run_puzzle_regressions.py`'s own module docstring documents exactly why `puzzle_catalog_check.gd` shares that project ("PuzzleCatalog depends only on PuzzleDefinition, so it is safe to add directly to the existing pure-rule-isolation project rather than a new temporary project") — `PuzzleAnalyzer` has the identical dependency footprint (`PuzzleDefinition`, `PuzzleState`, `PuzzleSolver` only), so the same reasoning applies without modification.
- **Alternatives considered**: A fourth isolated temp project dedicated to the analyzer — rejected, would duplicate `project.godot` scaffolding and add a subprocess invocation for zero additional isolation benefit given the identical dependency set.

## Decision: The developer report is a separate, non-gating script/launcher pair

- **Decision**: `tests/puzzle_structural_report.gd` (a headless `SceneTree` script using `PuzzleCatalog` + `PuzzleAnalyzer` directly, printing deterministic per-puzzle facts and the nine FR-021 comparison answers) is invoked by its own small `tests/run_puzzle_structural_report.py` launcher, separate from `run_puzzle_regressions.py`. It has no `check()`/`failures` counter and no `PUZZLE_*_FAILURES=0` marker — it always exits 0 when it runs to completion, since it reports facts, not pass/fail assertions.
- **Rationale**: FR-021 requires the report to answer comparison questions "deterministically" but explicitly forbids it being "a new in-game analytics screen," and the spec's broader stance (FR-009/FR-023) forbids anything that looks like a composite pass/fail difficulty judgment. Keeping it out of the required-green gate avoids any reader mistaking "the report ran" for "the puzzles passed a difficulty check."
- **Alternatives considered**: Folding report generation into `puzzle_catalog_check.gd`'s existing `_initialize()` — rejected, would conflate a factual comparison printout with the gate's pass/fail semantics and force every regression run to print report output even when only correctness matters.

## Decision: Calibration worksheet, records, and findings summary are plain markdown inside this spec's own `.devspark.work/` bundle

- **Decision**: `calibration/worksheet-template.md` (blank, reusable per-puzzle template matching FR-022's exact fields), `calibration/records.md` (the six filled-in entries), and `calibration/findings-summary.md` (the FR-026 deliverable) live under `.devspark.work/specs/006-spec-puzzle-structure-analysis/calibration/`.
- **Rationale**: The constitution and this repo's four-root placement convention (AGENTS.md) reserve `.knowledge/` for current, validated, durable truth — a per-puzzle subjective worksheet and a "supported/contradicted/inconclusive" findings summary are exactly the kind of hypothesis-in-progress content that must not live there yet. Keeping it inside the spec's own temporary bundle satisfies FR-022/FR-026's "no persistence infrastructure" requirement (it is just files) while still being reviewable during this spec's own lifecycle.
- **Alternatives considered**: A new `docs/` directory at repo root — rejected, introduces a new top-level convention for content this spec's own Rationale Summary already frames as non-durable; `.knowledge/product/` — rejected, would misrepresent an unvalidated hypothesis log as authoritative product truth, which FR-025/FR-026 explicitly forbid.

## Decision: Six new puzzles are authored as literal `PuzzleCatalog` builders, targeting the pre-spec research's identified metric gaps

- **Decision**: Each of the six new builders follows the existing `_build_*()` literal-construction style (see `scripts/puzzle/puzzle_catalog.gd`'s eight existing builders), sized and shaped to deliberately hit its named experiment's structural target as identified in `.devspark.work/research/pre-spec-006-puzzle-difficulty-research.md` (e.g. the Cascade/Key Arrow puzzle needs a single arrow whose removal drops the in-degree of ≥2 other arrows to zero simultaneously; the Dense Unravel puzzle needs occupied-cell density well above the existing catalog's 0.20–0.50 range *combined with* a forced/branching-state ratio that is not ~100% immediately legal like `dense_board`).
- **Rationale**: The pre-spec research already computed exact metrics for all eight existing puzzles (and the unshipped `create_fixed()` board) via a from-scratch Python re-implementation, giving concrete numeric targets to author against and verify each new puzzle clears its own `PuzzleAnalyzer`-reported threshold before being considered complete (spec FR-004 through FR-018, User Story 2 acceptance scenarios).
- **Alternatives considered**: Authoring the six puzzles first and only afterward checking whether they happen to hit the target metrics — rejected as backwards; the spec's edge case explicitly requires revising any puzzle whose analyzer output doesn't confirm its intended property before shipping it, so authoring-with-a-numeric-target-in-hand is the more direct path.
