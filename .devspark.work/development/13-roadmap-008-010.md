The order is deliberate. Content authored before 008 would be distorted by screen size. A web build before 009 would put weak puzzles in front of the first outside players. Generation stays last because it would optimize metrics that human playtesting has not validated (DP-022, DP-025).

## Spec 009: Gordian Knot Experiments

### Question

> What kind of hard puzzle is satisfying to untangle?

### Hypotheses under test (from 05-puzzle-design-research.md)

- **H1.** Difficulty is driven by *geometric entanglement* (long, bent arrows whose tails occupy each other's neighborhoods), not by arrow count or dependency depth alone. Spec 006 found that dependency metrics were not enough.
- **H2.** Removing a highly entangled arrow produces a visible simplification, and that is the reward.
- **H3.** There is a readability boundary ("spaghetti") past which entanglement stops being satisfying and becomes annoying. It can be located.
- **H4.** Zoom and pan help reasoning: whole knot, then local trace, then whole knot again.

### Scope

1. **Author 4-6 hand-built experimental puzzles** in `PuzzleCatalog`, marked experimental like the six from the 006 work:
   - **A, Long Lines:** moderate board, 8-10 arrows, most 3-6+ cells, several bends, whitespace remains. Baseline payoff of long geometry.
   - **B, Interwoven:** 10-14 arrows, tails in each other's visual neighborhoods, cross-board relationships.
   - **C, Dense Knot:** 15-20 arrows, multi-bend, dense center, dependencies created mostly by tails.
   - **D, Spaghetti:** deliberately over-entangled, to find the boundary.
   - Optional, only if A-D leave a gap: E, one huge key arrow that transforms the board when removed; F, regional knot with an open perimeter.
2. **Extend `PuzzleAnalyzer` with descriptive geometry metrics**: long-arrow ratio, single-cell ratio, bends per arrow, and cells cleared per removal. Report only. They must not gate anything (DP-018).
3. **Gate the puzzles on solvability and on structure, not on difficulty.** Every experimental puzzle must pass the solver and the existing catalog regression gate.
4. **Run a structured playtest** using the questions in 10-roadmap.md ("How long before the first confident move?", "Did you trace or scan heads?", "Any aha?", and so on). Record Open Move use, mistakes, score and time per puzzle.
5. **Write the findings** as a knowledge note: which geometry produced satisfaction, which produced annoyance, where the spaghetti boundary sits, and which puzzles are keepers.

### Non-goals

Procedural generation. A single "difficulty score". New removal rules. Persistence. Web. Telemetry. Player identity. Any change to scoring.

### Entry criteria

- 008 complete and merged, with its manual end-to-end checks passed.
- The hand-off contract above is confirmed by playing the 008 validation puzzle, not only by reading its tests.

### Exit criteria (all required)

- Every experimental puzzle passes solver and catalog gates. `PUZZLE_*` failure markers are all 0.
- At least one playtest session is recorded for each of A-D. State the number of testers; one tester is evidence, not proof.
- H1-H4 each have a written verdict: supported, refuted, or inconclusive, with the evidence cited.
- A **keeper list** exists: the puzzles that ship in the playtest build, with the reason for each.
- The next-spec decision is recorded (see the gate in Spec 010).

### Risks

| Risk | Mitigation |
|---|---|
| Hand-authoring dense puzzles by literal coordinate is slow and error-prone. | Author small and use the solver as the check. If it is still painful, that is data for the eventual generator question; do not build the generator here. |
| A single playtester (the author) overfits to their own taste. | Require at least one outside tester before the exit review, even informally. |
| Analyzer metrics get treated as difficulty. | Metrics are labeled descriptive in the report and the knowledge note. Verdicts come from playtests. |
| 008's navigation feels bad on the densest boards, so results measure the camera, not the puzzle. | Record navigation friction separately from puzzle difficulty in the playtest notes. |

### Open questions for `/devspark.specify`

- Maximum board size to support. 008 sets the technical limit; 009 should choose what it actually needs.
- Are experimental puzzles shown in the main menu list, or behind a developer or experimental group? The 006 puzzles set a precedent to check.
- Is playtest logging manual (a notes template) or does it need in-game support? Prefer manual. In-game logging edges toward the feedback API, which is out of scope.

## Spec 010: Web Playtest Build

### Question

> Can a stranger click a link and play it, with no install and no login?

Proposed because 10-roadmap.md places Web immediately after "a few genuinely interesting puzzles", which is what 009 produces. **This is the one place I chose between options.** The alternative is to make 010 a second content round if 009's verdicts are weak. See the gate below.

### Scope

1. **Godot 4.4 Web export** hosted from the ArrowSpark repo (GitHub Pages is the obvious low-cost choice; confirm in planning). Prefer the single-threaded export so no special cross-origin headers are needed.
2. **The 009 keeper puzzles plus the original introductory ones**, playable end to end: Open Move, results, session scoring, replay.
3. **Touch and browser input**, deferred from 008: one-finger pan versus tap-to-select, pinch zoom, Fit Puzzle reachable on touch. Wheel and drag zoom on desktop browsers.
4. **Browser lifecycle:** resize, orientation change, focus loss, and audio starting only after a user gesture. The session scoreboard stays in memory, so a page reload starting fresh is expected and correct.
5. **A manual feedback path only**: a visible link to a form or issue template. No API, no telemetry, no identifier.
6. **CI or documented build steps** that produce the export reproducibly, plus the two existing regression gates still passing.

### Non-goals

Feedback API. Analytics. Accounts or persistence beyond the inherited settings. Mobile app stores. Monetization. Daily puzzles. Any change to puzzle rules or scoring.

### Gate to start (checkpoint after 009)

Start 010 as written only if 009 produced **at least 3 keeper puzzles** with a written reason and at least one outside tester's reaction. Otherwise the next spec is a second content round, and this Web spec moves down one slot. That is the point of revising after each spec.

### Entry criteria

- The 009 keeper list and findings note exist.
- 008 is not known to have unresolved navigation defects (or those defects are listed as 010 inputs).

### Exit criteria (all required)

- The build loads and plays the full keeper catalog in a current desktop browser and a current phone browser.
- Touch pan and pinch zoom work, and a tap selects the right arrow after any pan or zoom.
- Complete a puzzle, use Open Move, replay it, and see the session-best update, all in the browser.
- No login, no install, no persistent player identifier.
- The game plays normally if the feedback link or network is unavailable.
- Headless regression gates and the Godot validation are green. A browser smoke test is recorded (constitution Principle V extends to this platform).

### Risks

| Risk | Mitigation |
|---|---|
| Touch is a new input class and touch-versus-tap bugs are likely. | Reuse 008's pan/select arbitration. Test on a real phone, not only browser dev tools. |
| The Maaack template's menus and settings assume desktop and may misbehave in the browser (fullscreen, quit button, file paths). | Audit the template UI in planning. Hide or adapt desktop-only items rather than rewriting the template. |
| Web export performance on the largest puzzles. | Measure once with the biggest keeper. Do not build speculative optimization infrastructure. |
| Scope creep into "platform project". | The roadmap says Web must not become one. The non-goals above are the fence. |

### Open questions for `/devspark.specify`

- Hosting choice, and whether it builds in CI or is uploaded by hand.
- Whether settings persistence (inherited from the template) is acceptable in the browser. It is a settings store, not gameplay memory, so probably yes; confirm it against DP-005 and DP-006.

## Checkpoint after Spec 010

Run 2026-10-01 against `main` at `6e60e11`, comparing the plan to what shipped.

### What actually happened

- **008** shipped as planned and met the hand-off contract in its automated
  checks. Gamepad hardware and a few other scenarios were accepted as
  outstanding by its verify gate, so "did navigation feel good on the densest
  board" rests on the designer's play, not on a recorded study.
- **009** shipped six experimental puzzles (A-D of the plan became Long
  Geometry, Interwoven Paths, Dense Core, Boundary Knot, with Distinct Regions
  and Single Release covering the optional E/F ideas). Catalog 15 to 21.
- **010 diverged from this roadmap.** After 009 the project spent its next spec
  composing one reference level and adding purpose groups, instead of building
  Web. Catalog 21 to 22.

### Gate results

| Check | Result |
|---|---|
| 009 exit: every puzzle passes solver and catalog gates | **Met.** All `PUZZLE_*` markers 0. |
| 009 exit: at least one playtest per puzzle | **Partly met.** One aggregate author session; per-puzzle data unknown. |
| 009 exit: H1-H4 each with a written verdict | **Partly met.** An aggregate "supported" for long bent geometry (H1, H2). H3 (spaghetti boundary) and H4 (zoom helps) were not separately concluded. Treat as inconclusive. |
| 009 exit: keeper list | **Not found as a distinct artifact.** The Reference Knot absorbed the idea instead. |
| Web gate: 3 or more keepers and an outside tester | **Not met.** No outside tester has played anything. |

By the roadmap's own rule ("if a spec's question was not answered, do not
advance"), the honest reading is that the content question has one tester's
answer and needs outside players. Web Showcase is still the right next step
because it is how outside players arrive, but it must be specified as a
validation vehicle, not as a launch.

### Decisions to record

- The Web spec inherits the SC-009 protocol from
  `.devspark.work/specs/010-spec-reference-puzzle/deferred-to-next-spec.md`:
  minimal guidance, preserve first exposure, observe then interview one question
  at a time, record words as given.
- It also inherits touch input, which 008 deferred.
- Design boundary learned in 010: some freedom is good, many simultaneously
  obvious moves feel like clicking. Add as a design-principle candidate
  (DP-026 or later) once outside players confirm or refute it.
- Analyzer metrics stay descriptive. The longest-chain search is now linear-time
  on acyclic input; nothing new gates.

### Open questions for the next `/devspark.specify`

- Hosting and whether the export builds in CI (unchanged from above).
- How a Web player's first-exposure behavior is observed without telemetry:
  manual facilitated sessions, or a feedback link only.
- Is the Reference Knot the right first screen for a cold player, or should
  Foundations come first? SC-009 exists to answer this; do not pre-decide it.
- Whether the Puzzle Lab group should be visible in the public build.
- Whether the F3-style developer readout (removed in PR #4) is needed to capture
  real cell sizes during playtests.

### Updated order

1. **Web Showcase & Playtest** (next).
2. A second content round only if outside players reject the Reference Knot.
3. Anonymous feedback API, if manual feedback is too slow.
4. Difficulty characterization, then generation. Unchanged.

## Revision protocol

Run this checkpoint when a spec is marked Complete, before running `/devspark.specify` for the next one.

**After 008 completes**

- [ ] Did the hand-off contract hold? Note any navigation friction that would distort puzzle evaluation.
- [ ] Did 008 change board size limits, the catalog shape, or the analyzer? Update 009's open questions.
- [ ] Did any deferred item (touch, gamepad nuance) grow? Update 010.
- [ ] Are the 009 puzzle sizes still sensible given what the camera actually feels like?
- [ ] Refresh 08-current-state.md, README.md and 01-project-history.md (section 12, "Current Moment") to show 008 complete.

**After 009 completes**

- [ ] Verdict on H1-H4, with evidence.
- [ ] Apply the 010 gate: 3 or more keepers and an outside tester, or reorder.
- [ ] Does the analyzer now need new descriptive metrics, or are they noise?
- [ ] Does anything learned change the product principles in README.md or 11-design-principles-and-decisions.md? Add decisions as DP-026 onward.
- [ ] Decide what the spec after 010 is, and whether the feedback API is now warranted.

**After 010 completes**

- [ ] Did outside players finish puzzles? Where did they stall?
- [ ] Is manual feedback enough, or is the API now justified?
- [ ] Revisit the "after 010" list and write the next two-spec roadmap.

### Validation rules for every checkpoint

- Compare the plan to what actually shipped, not to what the spec said.
- Reconcile with `.knowledge/` (the durable truth) and with the code. Working specs are temporary (DP-024).
- If a spec's question was not answered, do not advance. Write a follow-up spec for the same question.
- Keep at most two future specs planned in detail. Anything further stays a one-line ordering.
